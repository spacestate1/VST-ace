vst-ace 0.3.1 -- release notes
==============================

  version   0.3.1
  commit    d906ff3         "studios: loading bar around plug-in loads, ..."
  tag       v0.3.1          NOT yet created -- see PUBLISHING

47 commits since 0.3.0. The tracker and both studio shells grew up: click-free
PipeWire sample output with recovery, per-track volume and meters, up to 16
tracks, a key map editor for sample sets, Record studio mix, Open Recent, MIDI
and effect input in the GTK shell, Connect > REAPER, and a choice of PipeWire,
JACK or ALSA for synth audio. See HANDOFF-2026-10-07 and HANDOFF-2026-10-08.

Last changes before this release:
  - Qt studio crashed closing a tab that had an "Inputs" submenu: the menu's
    own action was deleted a second time. Fixed.
  - Both studios show a "Loading" bar while a plug-in loads, instead of an
    unpainted window.
  - A sample track's octave is set from its sample set (the octave holding
    the set's lowest pad) every time the track is routed -- set picked, song
    opened, session restored, set edited -- and stays locked.

WHAT CHANGED
------------

MIDI both ways

  The out port existed in both windows and carried nothing. Everything
  played locally goes out of it now -- notes, bend, all-notes-off -- and
  thru echoes what arrives, so a tracker at the other end plays these and
  is played by them. Incoming MIDI reaches the plug-in as the raw messages
  it arrived as, where before only notes, bend and controller 123 got
  through: wheels, pedals, aftertouch and song position now arrive. A
  sequencer's clock drives the transport and the tempo box follows it.

The same inputs in both windows

  dwstudio gained what pestudio had: an audio device chooser, a line saying
  whether anything is actually arriving, the input-channel mask re-sent on
  every load, and the same four effect input sources -- silence, a sawtooth
  per held key, noise, or the microphone. An effect with two inputs now
  picks the keys by itself on load, so it makes a sound the moment it is
  opened.

Driven from the keyboard

  Ctrl+F, Ctrl+G, Ctrl+E and Escape move between the plug-in list, the
  programs, the editor and the keys; Ctrl+R rescans devices, Ctrl+T is
  thru, Ctrl+H connects the out port to hardware, Ctrl+. is panic, and
  Ctrl+Up and Ctrl+Down are the volume. Both windows, the same keys, all of
  them on the menus.

One window, not two halves

  The Engines/Plug-ins switcher is gone and the plug-in pane is the window.
  The engines stay as what sounds when nothing is loaded. Master volume
  moved to a short bar directly over the keys in both windows.

Playing while the editor has focus

  Turning a knob in a plug-in's editor used to kill the computer keyboard
  until the on-screen keys were clicked. The editor still forwards every
  key to the plug-in and now lets the ones the piano claims through, so
  tweak-then-play works the way round people actually do it.

Saying what went wrong

  A fault names the failing address from the ELF symbol table or the import
  table, dumps the instruction bytes, and recognises a guest stack overflow
  as one. A sampling profiler says which stub a slow load is sitting in --
  which is how Marvel GEQ's 25-second load became 0.74s. A stand-in that
  gets called reports itself, and the busiest ones are named, so a plug-in
  that draws nothing says what it was missing.

The loader

  7223 ordinal imports resolve by number, generated from Wine's export
  tables. Real VirtualProtect and VirtualQuery page bookkeeping, the
  CharUpper, BSTR, SList and timer-queue families, CRT float maths, time
  and stat, GDI+ regions and matrices, and a window layer that answers
  GetFocus, EnumWindows, menus and dialog items. A dead 32-bit bridge or
  out-of-process host is recovered rather than left silent. The Windows
  corpus goes from 51 of 59 loading to 57.

Also

  peload --play runs a plug-in headless from a MIDI port to a PipeWire
  sink. tools/vst_install.py unpacks .exe, .pkg and .dmg installers, so an
  official installer can be opened as if it were a plug-in.

The Arch package needs no VM -- this workstation is the target -- so it is
`bash packaging/build-arch.sh 0.3.0`, and it carries peload32 only because
multilib is enabled here.

Both were built from 2377625, before the packaging changes that came with
them. Those changes touch staging and the recipes, not a line of what gets
compiled, so the binaries in these three packages are the ones 2377625
produces. A rebuild after committing would name the newer commit and
produce the same programs.

The AppImage has not been built for release. It can only usefully be built
on the oldest distribution it is meant to run on, because glibc is the one
library it cannot carry: built here it wants 2.43, built on ubuntu24.04 it
wants 2.39 and runs on Ubuntu 24.04, Debian 13, Fedora 40 and Arch alike.
That VM is shut off, and this workstation is not in the libvirt group, so
starting it is a step only you can do:

  sudo virsh -c qemu:///system start ubuntu24.04

then the same rsync-and-build as the .deb, with:

  bash packaging/build-appimage.sh 0.3.0

It wants four tools that are not distribution packages -- linuxdeploy, its
Qt and GTK plugins, appimagetool -- and fetches them into
~/.cache/vst-ace/appimage-tools itself the first time.

A NOTE ON THE THREE PACKAGES ALREADY BUILT

They were built from 2377625, and the AppImage work changed c/src/dw.c:
`va` now looks for its helpers relative to its own path before falling back
to the one compiled in, which is what makes a mount point nobody knew at
build time work. That is a code change rather than a packaging one, so the
.deb, .rpm and Arch package in release/ predate it. They are correct as they
stand -- the compiled-in path is exactly right for an installed package, and
all three were tested that way -- but a release cut after this is committed
should rebuild all four from the same commit, so every artifact names it.
