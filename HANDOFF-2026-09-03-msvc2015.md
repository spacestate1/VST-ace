# Handoff — MSVC 2015 plug-ins, and where their editors stop

**Status: both editors draw in full. The VST3 loads, renders and paints its
whole interface; the i386 VST2 loads with 110 parameters and paints its whole
interface too, through the bridge as well as directly.**

Two earlier readings in this document were wrong, and both are worth keeping
for the shape of the error. "The reasons are not more host work" was wrong
twice over: the i386 build was blocked by six absent pieces of Win32 rather
than by its download, and the VST3's blank editor was four missing pieces of
Direct2D and a region call that answered zero. Neither was subtle once
something asked the plug-in what it wanted instead of reasoning about what it
ought to want.

## The one mistake, made eight times

Every blocker in this document is the same shape: **a stub returning 0, where 0
is the API's word for success.**

  * GDI+ `Status`: 0 is `Ok`
  * `HRESULT`: 0 is `S_OK`
  * `_initterm_e`: 0 is "every initialiser succeeded"
  * `scanf`: a count of 0 assignments is a legitimate answer
  * `GetModuleHandleEx`, `FindFirstChangeNotification`: 0 is failure here,
    which the caller reads as a reason to give up rather than as "nothing"

The generic stub in `missing_import()` returns 0 because that is the safe answer
for a `void` or a `BOOL`. For a status code it is the opposite of safe: it tells
the plug-in the call worked, so the plug-in takes the pointer it was never
given and faults somewhere else entirely, a long way from the stub. Every
diagnosis below was slow for that reason, and `stub_failure_value()` is where
the fix belongs — it now covers `gdiplus` (GenericError) and `d3d*`/`d2d*`/
`dxgi` (E_FAIL) as families rather than function by function.

**If a plug-in dies far from anything you changed, look for a stub whose zero
means yes.**

## The 2015 C runtime arrives under fifteen other names

`crt_alias()` mapped `msvcr*`, `msvcp*`, `vcruntime*` and `ucrtbase` onto the
one CRT implementation here. MSVC 2015 split the CRT into apiset DLLs —
`api-ms-win-crt-runtime-l1-1-0`, `-stdio-`, `-heap-`, `-convert-` and a dozen
more, each forwarding to ucrtbase — and none of them matched, so a 2015-built
plug-in imported its **entire** C runtime under names that fell through to the
generic stub.

`_initterm_e` is what made it fatal rather than merely wrong. It walks an array
of initialiser pointers and calls each, which is how a C++ module runs its
static constructors; stubbed, it reported success having run none. A
side-loaded MSVCP140 mapped, said it had initialised, and left every locale and
iostream global null. **With the alias added it runs 554 constructors instead
of none.** The implementation was already here under `msvcrt.dll`; only the
name was missing.

Matching is by prefix, because the apiset names carry a version suffix that
changes between Windows releases and some import tables truncate them.

## scanf did not exist

There was no `sscanf` in this host at all, so the UCRT's
`__stdio_common_vsscanf` fell to the stub. A SynthEdit plug-in parses its whole
module graph out of XML with it: every module id came back unset, every registry
lookup missed, and the plug-in crashed reading address `0x3c8` — which is
`lea rcx,[rax+0x3c8]` on a null `rax` two instructions after the lookup, in a
function whose *next* block tests the same pointer before using it.

Written out rather than delegated, for the same reason `w32_vfmt` is: on x86-64
the guest passes Microsoft's `va_list` and the host's `vsscanf` expects System
V's, so every argument pointer would be read from the wrong register or slot.

**Windows `long` is 32 bits.** `%ld` stores four bytes here, not eight. Storing
eight scribbles on whatever the guest put beside the variable, silently.

With scanf the plug-in loads: 235 parameters. The wide CRT beside it —
`wcslen` was the only `wcs*` present — is what makes those parameters *named*.

## dynamic_cast

`__RTDynamicCast` was a generic stub. A stub returning 0 is not a soft failure:
the compiler emits a null check only where the source admits the cast can fail,
so a cast the programmer knows cannot fail is used immediately.

Found by disassembly, not guessed. The faulting call target was an import
thunk; its IAT slot at `0x19d988` resolved to `VCRUNTIME140.dll!__RTDynamicCast`.

The implementation walks MSVC's own RTTI: the vftable is preceded by a
`CompleteObjectLocator` naming the type, saying where the subobject sits inside
the complete object, and pointing at a hierarchy descriptor listing every base.
Two details matter:

  * **Compare mangled names, not TypeDescriptor addresses.** A class defined in
    two images has two descriptors. MSVC's own runtime compares names for this
    reason.
  * The locator carries its own RVA, which is how an object works out where its
    RTTI lives without the host knowing which module it came from.

Instrumented over a load it does 15,384 successful casts. The failures — 4,656
to `ug_container`, 2,804 to `ug_patch_automator` — are ordinary type tests, and
are not logged for that reason.

## A plug-in could not find out where it was

`GetModuleFileName` answered with a fixed `C:\peload\plugin.dll` whatever was
loaded. Enough for a plug-in that wants *a* name; wrong for the very common one
that takes the directory out of it and loads its own data from beside itself —
`path_norm_n` maps that to `/peload/`, which holds nothing. SynthEdit asks for
its `.sem` modules that way and got seven nulls in a row.

The real path goes back now, separators flipped and a drive letter in front, so
a guest splitting on a backslash finds the right pieces and `path_norm_n` turns
whatever it rebuilds back into the host path it came from. Set for the plug-in
only, and **saved across a runtime side-load** — an msvcp140 mapped out of
`runtime/` must not become the answer to "where am I".

## LoadLibrary could not load a library

It only ever answered for the system DLLs this host shims. Everything else got
NULL — including a file sitting right there that this program, a PE loader,
knows exactly how to map. A plug-in shipping part of itself as separate DLLs got
nothing.

`winstubs.h` has no loader of its own and is shared by two that differ in width,
so each installs a pair of hooks (`winstubs_set_loader`) and LoadLibrary reaches
the real thing through them. A wrong-width DLL simply fails to map, which is the
right answer rather than a special case. Modules are kept in a table so one
asked for repeatedly is mapped once and keeps the same handle.

`GetProcAddress` asks a real module for its own exports **first** — the module
really does define those names and a same-named stub would shadow the genuine
one — and **falls through on a miss** rather than returning. An early return
there broke every `GetProcAddress` on a handle that is not ours, which had been
resolving through the name search below it.

`LoadLibraryExA` was missing while the W form was present. That is what the
delay-load helper reaches for; without it the first delay-loaded import raised
`0xC06D007E`.

## What the plug-in told us once its stdio worked

Implementing `__acrt_iob_func` and `__stdio_common_vfprintf` was worth more than
the calls themselves. The plug-in immediately printed:

    ERROR: Unexpected NULL from FindFirstChangeNotification.

It watches its own folder so it can pick up a skin dropped in beside it, and
read the null as a failure of the host rather than as "no changes" — then
abandoned building its DSP graph, which rendered silence with no other symptom.
An unsignalled event is the right object: a watcher polling it times out, which
is what it expects.

`WaitForMultipleObjects` came with it, and a stub there is worse than a missing
one: it returns 0, which is `WAIT_OBJECT_0`, so the watcher is told its files
changed on every pass.

**Give a plug-in somewhere to print. It will tell you what is wrong.**

## New subsystems

Three, all under `#ifndef PELOAD_NO_GUI_LAYER`, all built on machinery that was
already here:

  * **WIC** (`dwrite_shim.h`) — `CoCreateInstance` was not implemented at all,
    so a plug-in asking COM for an `IWICImagingFactory` got nothing and left the
    pointer null in a structure it then used. Decoding only: name a file, get its
    pixels, through the `png_in.h` readers written for the macOS side's ImageIO.
    MinimogueVA decodes all 96 of its images through it.
  * **DirectWrite's other half** (`dwrite_shim.h`) — this shim was written for
    Skia, which lays text out itself. `GetSystemFontCollection` handed back a
    bare probe, because Skia registers a collection of its own and never asks for
    the system one. Added the collection, family, font, face-name and
    localised-string objects, `GetGdiInterop`, `CreateTextFormat` and
    `CreateTextLayout`.
  * **GDI+** (`gdiplus_shim.h`, new, ~1170 lines) — the 96 entry points this
    corpus imports. A DC's pixels are a `w32_surf`, glyphs come from the same
    FreeType face DirectWrite measures with, images decode through `png_in.h`;
    the one piece genuinely missing was a rasteriser, which flattens curves to
    segments and fills by scanline under either winding rule, sampling four
    times vertically.

`GetDeviceCaps` deserves its own line. A stub answering 0 is not neutral:
`LOGPIXELSX` is the display DPI and a plug-in scales its whole layout by
`dpi/96`, so zero collapsed the interface to nothing. **That alone was the 0x0
editor.**

## Where each editor stops

### The VST3: Direct3D 11 — walked, not emulated

The first reading of this was wrong and is worth recording, because the
correction is the useful part.

Chased to the end rather than assumed:

  * The editor's device-creation function (`FUN_1800d1c20`, RVA `0xd1c20`) calls
    `D3D11CreateDevice` and then dereferences the device **without checking**.
  * Its unwind info is `UNW_FLAG_UHANDLER` only — that runs during unwinding, it
    does not catch. Both call sites (`0xd2660`, `0xd4690`) have no `EHANDLER`
    either. **There is no `__try` anywhere in the chain**, so implementing SEH
    dispatch would let it unwind and die rather than recover.
  * Its paint loop checks `DXGI_STATUS_OCCLUDED`, which is a swap-chain present
    loop. No renderer selection to steer, no version check to spoof — the
    `GetVersionExW` call in that function is a feature check *inside* the D3D
    path, not a choice between paths.

It imports four renderers (`d3d11`, `d2d1`, `gdiplus`, `opengl32`) and commits
to the first.

**What that first reading missed is that the plug-in only walks *through* D3D to
reach Direct2D, and Direct2D's drawing is ordinary 2D.** Nothing has to touch
hardware. `d3d_shim.h` provides the walk and nothing more: a device, an adapter,
a DXGI factory, a swap chain whose back buffer is the window's own pixels, and
the query-interface chain between them. Direct2D is where the work would happen,
and it renders into the same `w32_surf` a GDI+ graphics object writes to.

The whole chain runs:

    D3D11CreateDevice -> IDXGIDevice -> GetAdapter -> GetParent(IDXGIFactory2)
      -> CreateSwapChainForHwnd -> ID2D1Factory1::CreateDevice
      -> CreateDeviceContext -> GetBuffer -> CreateBitmapFromDxgiSurface
      -> SetTarget

**The editor opens and captures at 1004x590 where before it took the plug-in
down.** It draws nothing yet — see below.

Three traps on the way, each worth its own line:

  * **Probe vtables were 64 slots.** `ID3D11DeviceContext` has 108 methods and
    `ID2D1DeviceContext` is not far behind, so a call past the end landed on
    whatever followed the array. That presents as a jump to a null address with
    nothing at all to say why. 160 now.
  * **QueryInterface returned the same object for every interface**, so slot
    numbers from four vtables collided in the log and were worse than useless.
    Each interface is its own object now, and an unrecognised GUID is printed in
    full rather than guessed at from a slot number.
  * **The swap chain's HWND was ignored.** A plug-in nests its drawing window
    inside the one it was given — VSTGUI inside the container, the GMPI surface
    inside that — and it is the innermost that Direct2D targets. Drawing into the
    display window put the pixels where nothing was reading.

### Where it stopped, and why it does not any more

**Resolved.** The section below was written when the editor drew nothing, and
its reading -- that GMPI never marks its controls dirty -- was wrong in an
instructive way. The dirty list is not filled by GMPI at all. The paint handler
builds it from `GetUpdateRgn` and `GetRegionData`, and this host's
`GetRegionData` returned 0:

    n = GetRegionData(hrgn, 0, NULL);
    if (n != 0) { ... add each rect to the list ... }

The stub's comment supposed a caller would fall back to `GetRgnBox`. This one
does not; zero means the region is empty, so the list stayed empty and the
handler returned without calling a single Direct2D method -- which is exactly
what the note below observed, and attributed to the plug-in.

Three more, once it was drawing: `SetTransform` discarded the matrix, so the
whole interface drew at the origin on top of itself; `GetTransform` did not
exist and is read 298 times a paint; and there were no bitmaps at all, which is
most of what a skin is. `IWICImagingFactory::CreateBitmap` is where the panel
every other control sits on gets composed.

The original note follows, because the way it was wrong is the useful part.

### Where it stopped (superseded)

The plug-in's paint handler (`FUN_1800d2660`, the `GMPIGUI` window procedure's
message handler, RVA `0xd2660`) gates its drawing on two things:

    if (self[0xf] != 0 && self[10] != self[0xb]) { ... draw ... }

The second is a begin/end pair over its own **dirty rectangle list**. With that
list empty it returns without calling a single Direct2D method — not one, so
there is not even an `E_NOTIMPL` to follow. `WM_PAINT` is delivered and
`ValidateRect` is called at the top of the handler, so the message plumbing is
working; what is missing is whatever makes GMPI mark its own controls dirty.

The next person should start there: find what adds to that list (a layout pass,
a parameter notification, a resize) and what this host is not doing that would
trigger it. Everything downstream of it is already in place.

**The GDI+ work does not open this editor.** It is still right: the surface is
real, other plug-ins use it, and chasing it is what found the
`D3D11CreateDevice` `S_OK`.

### The i386 VST2: six missing pieces of Win32, not the download

Its imports are `GDI32`/`USER32`/`COMCTL32` — a classic GDI SynthEdit editor
built on MFC. **It loads now, with 110 parameters, and its editor opens at
1002x589.** The earlier reading — blocked by the download rather than the host —
was wrong, and worth recording because of how it was wrong: the missing modules
are real, and the plug-in survives them. Every actual blocker was a stub.

The chain, each step found by following the failure to the stub that caused it:

  1. **No i386 exception dispatch.** A throw reached `RaiseException` and
     aborted. Now walked; see the i386 half of `mscxxeh.h`.
  2. **The thrown type, once anything could report it:** `CMemoryException`,
     which is MFC's answer to a failed allocation, not to a missing module.
  3. **`LocalReAlloc`** was stubbed, so NULL, so out of memory — on a 32-byte
     allocation. With the Local/Global family implemented the plug-in loads.
  4. **`SetWindowsHookEx`** returning NULL makes MFC throw the same exception
     from inside window creation, and the `HCBT_CREATEWND` that follows is how
     it attaches its `CWnd`.
  5. **`CreateDIBSection`** did not exist at either width, and MFC reads NULL
     from it as out of memory too.
  6. **The USER32 rectangle family**, none of which existed. A layout that
     offsets a rectangle and gets it back unmoved never converges: an endless
     `SelectObject` pair and a stack overflow 72 frames deep.
  7. **`RectVisible`** answering 0 tells a plug-in none of its interface is
     visible, and it draws none of it — zero drawing calls into a correctly
     built window.

It renders too, at peak 0.5199, and every one of its SynthEdit modules loads:
the run that produced this document reported seven "Can't load Module" failures
and there are now none. They were never a missing download -- a 2007 SynthEdit
build carries its standard modules inside the DLL -- they were the same host
gaps as everything else here, and they went with them.

The `.sem` files beside the 2025 VST3 are a separate thing and are still
x86-64 only; nothing needs them.

### Why the editor tab is safe to click

Both failures killed the plug-in — the hang (`GetWindowInfo` never reporting a
size, so the caller polled forever) took the helper down and the audio with it.

There was briefly a guard for this: `pehost_editor_kind()` declined to open an
editor when the image imported Direct3D or Direct2D. **It is gone, and it should
be.** What made the editor fatal was `D3D11CreateDevice` returning `S_OK` with
no device, and the plug-in dereferencing what it was told it had. The walk in
`d3d_shim.h` returns real objects at every step, so there is no null to follow
and nothing to decline: the editor opens, captures, and leaves audio alone.

Declining would now cost the working editor for no gain, which is why the check
was removed rather than repaired.

No plug-in in the corpus imports Direct3D, Direct2D or GDI+, so nothing there is
affected by the shim either way.

## Runtime DLLs

`runtime/` and `runtime32/` are gitignored and **must stay that way** — they are
Microsoft's, not ours.

    runtime/    msvcp120.dll  msvcp140.dll  msvcp140_1.dll
                vcruntime140.dll  vcruntime140_1.dll
    runtime32/  msvcp120.dll  msvcr120.dll

**Wine's copies do not work** and are not a substitute: they are compiled
against Wine's ntdll and fault in their own startup. `find_real_dll()` refuses
Wine's directories for that reason. Telling them apart: Wine's carry a "Wine
builtin" marker and are roughly double the size — msvcp120 is 660 KB from
Microsoft and 1.2 MB from Wine. Most copies on a machine with Proton installed
are Wine's; a game that installed the real redistributable leaves genuine ones
in its prefix's `system32`/`syswow64`.

The 32-bit set is what the NI four need; without `runtime32/` they fall to the
arity stubs and the stack drifts.

## Reproducing

    # loads, renders, 234 named parameters
    ./peload/build/peload "…/MinimogueVA.vst3" --render out.wav --secs 2 --note 60

    # declines cleanly, audio unaffected
    ./peload/build/peload "…/MinimogueVA.vst3" --editor shot.ppm

    PELOAD_VERBOSE=1 …          # every stub on first call, [dwrite]/[wic] traces

Locating a crash without symbols, which is how most of this was found:

    gdb -batch -nx -ex run -ex "printf \"%p\n\", $rip" -ex "info proc mappings" \
        --args ./peload/build/peload "<plug-in>" --params
    # the r-xp anonymous region is the image; rip - region_start + .text RVA
    # is the RVA. Then:
    objdump -D -b binary -m i386:x86-64 -M intel --adjust-vma=<addr> chunk.bin

If the faulting instruction is `call [rip+…]`, that target is an IAT slot: parse
the import table and it names the stub that lied. That is how `__RTDynamicCast`
and `D3D11CreateDevice` were both identified.

Ghidra is set up here (`/opt/ghidra`, `scripts/DecompileAll.java`,
`DumpRttiClasses.java`). `analyzeHeadless … -process <prog> -noanalysis` reuses
an analysed project, which makes a second question cheap.

## Known-imperfect, deliberately

  * **GDI+ strokes** are a filled quad per segment; joins are not mitred. At the
    widths a panel outline uses the difference is invisible, and a proper join
    needs the whole outline offset.
  * **GDI+ gradients** interpolate along their axis only; a preset blend keeps
    its end colours and drops the intermediate stops. A path gradient is
    approximated by centre and first surround colour.
  * **`GdipAddPathString`** adds the text's box, not its outlines. Bounds and
    hit-testing stay right where drawing it would be wrong.
  * **Images** scale nearest-neighbour, and only the alpha row of a colour
    matrix is honoured — which is what a plug-in uses one for here, fading a
    disabled control.
  * **`WaitForMultipleObjects`** polls at 1 ms rather than waiting on a shared
    condition variable. It gets the answers right, which is the part callers
    branch on; the handle table is not built for the alternative.
  * **Dash patterns** are accepted and ignored. A dashed outline drawn solid is
    cosmetic; refusing the call is a control that does not appear.
  * **WIC** decodes only. No encoding, metadata, palettes or colour management.
  * **Direct3D** is a walk, not an implementation. Anything that would touch
    hardware answers no; the swap chain presents by copying the plug-in's
    window into the one the host reads, because there is no compositor here to
    walk child windows and this is the only child that draws.

## Two subsystems added since

### GDI, for plug-ins that draw with it rather than blitting

`win32gui.h` was written for plug-ins that rasterise their own interface and
blit the result -- iPlug2 with Skia. A GDI-era editor asks GDI to draw, and most
of what it asks for was a no-op returning success: `SetTextColor`, `MoveToEx`,
`LineTo`, `Ellipse` and `DrawText` discarded their arguments, pens and brushes
were created and never selected, `CreatePen` threw its colour away, and
`CreateFontIndirect` stored no `LOGFONT` at all.

Real now, and general to any plug-in of that vintage: pen/brush/font selection
and the DC state behind it, `Rectangle`, `PatBlt`, `SetPixel`, `GetPixel`,
`Polyline`, and `TextOut`/`ExtTextOut`/`DrawText`/`GetTextExtentPoint`/
`GetTextMetrics` rasterised through the FreeType face DirectWrite already owned.
Text had been measured at a flat seven pixels per character.

Three were wrong rather than absent, and each is the kind that survives review:

  * **COLORREF is `0x00BBGGRR`** and these surfaces are `0x00RRGGBB`. `FillRect`
    wrote one into the other, so every GDI fill had red and blue swapped --
    invisible while the only fills were grey.
  * **`GetStockObject` returned a brush for every index**, so selecting
    `BLACK_PEN` set the DC's brush and a plug-in outlining a shape filled it.
  * **`RectVisible` did not exist.** It cannot fail, so nobody checks it, so a
    stub answering 0 says "none of your interface is visible" and a well-written
    plug-in draws none of it.

`CreateDIBSection` is new and is how a plug-in gets at its own pixels; 32bpp
top-down aliases our surface, and the other layouts convert in whichever
direction is newer. Syncing unconditionally gets that exactly wrong -- it copies
the untouched buffer over GDI's drawing, so each call erases the one before.

**The heap now knows its own pointers.** A plug-in frees things it never got
from us and frees things twice, and that went straight to glibc: a wild pointer
took the host down, a plausible one corrupted the heap quietly. The quiet one
cost a long chase -- an MFC editor faulting inside its own
`CMapPtrToPtr::Lookup` on a bucket array full of small integers. A header in
front of each block was the first attempt and is wrong, because validating a
foreign pointer then reads the bytes before it; ASan said so on the first run,
on a `FormatMessage` buffer that was `malloc`'d and `LocalFree`'d, which is
correct on Windows where malloc *is* HeapAlloc. The table is to one side now,
and every stub handing back a buffer the caller frees allocates through it.

**ASan is worth knowing about here.** 32-bit works:

    cc -m32 -fsanitize=address -O1 -g -I peload -o /tmp/p32 peload/pe32.c \
       -lpthread -lm -L/usr/lib32 -lfreetype /usr/lib32/libX11.so \
       -lpipewire-0.3 -lasound

It found the first corruption in one run, and it makes a layout-sensitive
overrun survivable, which is how the i386 editor was made to complete at all.

### The MSVC C++ library, so its DLL is optional

`msvcp_shim.h`. `wants_real_image` side-loads `msvcp*` because it has an object
layout to get wrong -- a real reason, and not a permanent one. Every layout in
that file was read out of a real `msvcp140.dll` with objdump and the derivation
is recorded beside the code; the header comment is the place to start.

The classic locale's facets are deliberately not built. `use_facet` is a
template inlined into the plug-in, so when the locale does not have a facet the
plug-in's own code constructs it -- an empty vector is a working locale.

It is a **fallback**: a real msvcp is still preferred wherever installed, so
nothing that works today changes. Verified by moving `runtime/msvcp140.dll`
aside -- the plug-in loads, runs its initialisers, and stops one tier on
constructing a wide ostream.
